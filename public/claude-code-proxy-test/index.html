Why Browser Proxies Work While Claude Code CLI Still Leaks Your Real Region

One of the most confusing failures for developers is when Claude web chat opens cleanly in Chrome, yet running claude (Claude Code), Codex CLI, or Anthropic API scripts in the terminal immediately fails with a region restriction or account warning. The reason is architectural: browser extensions such as SwitchyOmega, Proxy Switchy, and anti-detect browser profiles only route traffic generated inside that browser process. Your shell—zsh, bash, PowerShell, Node.js, and Python—ignores browser-level proxy rules and sends HTTPS requests directly through your local ISP unless explicit terminal routing is configured.

Even when you turn on a system-wide proxy client, subtle CLI leaks remain common. Some tools honor HTTPS_PROXY and ALL_PROXY while ignoring macOS/Windows system proxy settings; others leak DNS lookups locally or fail over to direct IPv6 egress when only IPv4 TUN routing is enabled. Mixing a US browser session with direct non-supported terminal API calls on the same Anthropic account creates an instant multi-country login anomaly.

Use a two-layer audit before authenticating Claude Code. First, verify your browser profile right here on envguard.dev to confirm your exit IP is a clean non-hosting ASN (use a dedicated Static Residential ISP Proxy with code GXQVUA_081067 if flagged) with zero WebRTC leak and matching timezone. Second, run the open-source terminal checker github.com/fusae/claude-env-check directly inside the exact shell where you launch Claude Code. Confirm both browser and terminal exit through the same clean IP and supported region before signing in.
